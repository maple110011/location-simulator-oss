# 『位置模拟器』2.9.12 的模拟定位实现机制

本文只回答一个问题：这个 App 究竟用什么手段把 Android 的定位结果替换成用户选的坐标。所有结论都标注证据来源（路径相对于 `re-tools/jadx-out/`），并区分「已见」（在反编译代码或资源里直接读到）与「推断」（由代码行为推出、未能在本机运行验证）。

## 0. 一句话结论

这个 App 走的是 Android 官方的「模拟位置应用（mock location app）」通道：用户在开发者选项里把它设为模拟位置应用之后，它以前台服务每秒一次地向 `LocationManager` 的 `gps` 与 `network` 两个测试 provider 写入同一个坐标，同时通过 Google Play 服务的位置接口把同一坐标写成 Fused 定位的 mock 值；路线模拟则是在这条 1 秒 tick 的管线上，按速度沿折线推进插值点。它不依赖 root、不依赖 Xposed，唯一的系统级前置条件就是「被选为模拟位置应用」这个 AppOps 授权。

## 1. 注入通道一：LocationManager 测试 provider（已见）

核心代码在 `sources/com/example/mocklocation/service/MockLocationService.java`。

**建立 provider**（第 224-232 行 `c(String)`）：

```java
removeTestProvider(name);                                  // 先删除，保证幂等
addTestProvider(name,
    name.equals("network"),   // requiresNetwork
    name.equals("gps"),       // requiresSatellite
    false, false,             // requiresCell, hasMonetaryCost
    true, true, true,         // supportsAltitude, supportsSpeed, supportsBearing
    1, 1);                    // powerRequirement=POWER_LOW, accuracy=ACCURACY_FINE
setTestProviderEnabled(name, true);
```

`gps` 与 `network` 两个 provider 都被接管，所以无论目标应用监听哪个 provider，拿到的都是 App 写入的坐标。

**清理 provider**（第 206-222 行 `b()`）：对两个 provider 依次 `setTestProviderEnabled(false)` 与 `removeTestProvider`，两处都各自 try/catch，避免一个失败影响另一个。

**构造 Location**（第 89-106 行静态方法 `d(String provider, c point, float accuracy, long time, long elapsedNanos)`）：

| 字段 | 取值 | 说明 |
|---|---|---|
| provider | `"gps"` / `"network"` | 与目标 provider 同名 |
| latitude / longitude | 当前模拟点 | 路线模式里是插值点 |
| altitude | 0.0 | 固定 |
| accuracy | gps 3.0 米 / network 10.0 米 | 两条通道精度不同 |
| time | `System.currentTimeMillis()` | 每次 tick 重新取 |
| elapsedRealtimeNanos | `SystemClock.elapsedRealtimeNanos()` | 每次 tick 重新取 |
| bearing / speed | 当前点携带的航向与速度 | 路线模式由折线方向与设定速度给出 |
| Android 8.0（API 26）以上追加 | verticalAccuracyMeters = accuracy、speedAccuracyMetersPerSecond = 0.2、bearingAccuracyDegrees = 2.0 | 让 mock 值在精度字段上更自洽 |

**写入**（第 303-344 行 `h(c)`）：先 `setTestProviderStatus(provider, 2, null, now)`（2 = AVAILABLE），再 `setTestProviderLocation(provider, location)`；gps 与 network 各做一次，各自独立 try/catch 并汇总为 Result，只要有一个 provider 抛错就整体判定为失败（第 336-343 行）。失败时进入 `j(Throwable)`：记录 `Log.e("MockLocationService", "Mock location failed", th)`、把错误文案推给 UI 状态、清理 provider、释放 WakeLock、停止前台与自身（第 359-378 行）。

## 2. 注入通道二：Google Play 服务的 Fused 定位 mock（已见）

只写 LocationManager 的测试 provider 有一个现实缺口：很多应用用 `FusedLocationProviderClient` 取位置，走的是 Google Play 服务的融合定位，不会读到 `LocationManager` 的测试 provider。这个 App 同时把同一坐标写进 GMS：

1. 启动时先开 mock 模式：`((p070q1.a) this.f9526c.a()).g(true)`（第 175-177 行）。`p070q1.a` 是 `LocationServices.getFusedLocationProviderClient()` 的混淆封装，`g(boolean)` 内部以 API id **2420** 发起 GMS 请求（`sources/p070q1/a.java` 第 51-76 行），对应 `setMockMode(boolean)`。
2. 每次 tick 写入 mock 值：把 gps 那个 Location 复制一份、`setProvider("fused")`，然后构造 `G1.g` 请求，`f881b = 2421`（API id，对应 `setMockLocation(Location)`），回调对象是 `new c0.h(25, location)`（第 325-335 行）。
3. `c0.h` 的第 25 号分支在拿到 GMS 服务端的 `IGoogleLocationManagerService` 代理后，检查服务端是否支持 `set_mock_location_with_callback`：
   - 支持且版本 >= 1：写入 Location 与一个 callback binder，`transact(85, ...)`（`sources/c0/h.java` 第 320-341 行）；
   - 不支持：`transact(13, ...)`，即老版本 GMS 的 `setMockLocation` 事务码（同上第 342-346 行）。

**为什么它要自己搭这层 binder，而不用公开的 `FusedLocationProviderClient.setMockMode()/setMockLocation()`**：推断有两个原因。第一，公开 API 在旧版 GMS 上对 mock 的支持不一致，事务 85 的带回调变体只在较新版本存在，自己按服务端声明做能力选择更稳。第二，公开 API 的 Task 回调链路对「mock 是否真的被接受」的反馈更弱，而这个 App 需要把失败原因呈现到通知与界面上（第 336-343 行的「No mock provider accepted the location」）。这两点是推断，因为代码里没有注释说明动机。

## 3. 1 秒 tick 的主循环（已见）

`sources/com/example/mocklocation/service/MockLocationService.java`：

- 字段 `f9527d` 是主线程 Handler，`f9535m = new o(3, this)` 是每 tick 执行的 Runnable（第 80-87 行）。
- `a(d state, c point)`（第 111-204 行）是完整的一次 tick：
  1. `handler.removeCallbacks(oVar)` 先摘掉上一 tick，保证不会叠加；
  2. 对 gps、network 各调一次 `c(provider)` 重建测试 provider（幂等）；两者都失败才报「No mock provider is available」；
  3. 检查 `ACCESS_FINE_LOCATION` 是否已授权（`p010c1.d.f4077d.b(this, p010c1.e.f4078a) == 0`），已授权才开 GMS mock 模式；
  4. 保存 UI 状态对象 `d state`，调用 `h(c)` 写入本 tick 的坐标；
  5. 首次注入成功后申请 `PARTIAL_WAKE_LOCK`（标志 1），名字 `<包名>:MockLocation`，`setReferenceCounted(false)`，保证熄屏后仍按秒注入（第 188-196 行）；
  6. 刷新前台通知（第 201 行 `notify(1001, e())`）；
  7. `handler.postDelayed(oVar, 1000L)` 排下一次（第 202 行）。
- 停止时（`k()`，第 380-396 行）：摘掉 tick、重置状态、清理 provider、释放 WakeLock、`stopForeground`、`stopSelf`。

## 4. 路线模拟的推进算法（已见）

路线不是提前生成轨迹动画，而是在每个 tick 里按「已走距离」在折线上取插值点。

- 启动参数（`onStartCommand` 的 `START_ROUTE` 分支，第 476-524 行）：`route_latitudes[]`、`route_longitudes[]`、`route_speed_mps`、`route_loop`。点数少于 2 或速度 <= 0 会以 `route_invalid` 文案失败。
- 折线总长：对相邻点逐个调用 `p092v1.c.j(pointA, pointB)` 求距离并累加（第 510-512 行）；总长 <= 0.01 米同样判为无效路线。
- 当前点：`p092v1.c.x(points, distance)`（第 517 行）按累计距离在折线上做插值，给出坐标、该段航向（`bearing`）与速度。
- 进度：状态对象里的已走距离除以总长得到百分比，通知里以 `route_running_status`（「Moving at %1$.1f km/h · %2$d%%」）显示；暂停时显示 `route_paused_status`（「Route paused · %1$d%%」）。
- 速度单位：内部一律米/秒，展示时乘 3.6 换成 km/h（第 252 行 `dVar.f1372f * 3.6d`）。
- 暂停/恢复：`l()`（第 398-412 行）在路线模式且未结束时翻转 `paused` 标志，并用 `SystemClock.elapsedRealtime()` 记下时间基准，避免暂停期间累计位移。
- 循环与结束：`route_loop` 为真时到终点后从头继续；否则到终点后「保持最终位置」（对应文案 `route_completed`：Route completed · holding final location）。
- 单点模式：`START_MOCK` 分支构造状态对象后每次都写入同一个 LatLng，速度与航向为 0（第 460-466 行）。

## 5. 前台服务与通知（已见）

- 通知渠道：`MockLocationServiceChannel`，名称取自 `mock_service_channel_name`，描述 `mock_service_channel_description`，无声音、无振动、不显示角标（第 419-432 行）。
- 通知 id 固定 1001；标题在单点模式是 `mock_running_title`（Mock location is running），路线模式是 `route_running_title`（Route simulation is running）；正文是「纬度, 经度」，路线模式再拼上 km/h；坐标还没就绪时显示 `fetching_location`。
- 两个动作按钮：`TOGGLE_ROUTE_PAUSE`（路线模式下才出现，文案在暂停/恢复间切换）与 `STOP_MOCK`（停止模拟）；点击通知主体回到 `MainActivity`。
- Android 8.0 以上建渠道；启动前台时按系统版本分别走 API 34+/29+ 的带类型 `startForeground`，类型为 `FOREGROUND_SERVICE_LOCATION`。

## 6. 进程与生命周期（已见）

- `onStartCommand` 在模拟运行中返回 **3**（`START_REDELIVER_INTENT`），系统重建服务时会把最后的 Intent 重投，于是 START_MOCK/START_ROUTE 能在进程被杀后自动恢复；未运行时返回 2（`START_STICKY`）并只做清理（第 541-544 行）。
- `onDestroy` 兜底：摘 tick、清 provider、释放 WakeLock（第 434-441 行）。
- 服务通过 `onBind` 暴露 Binder（`f9524a`），`MainActivity` 绑定它来接收状态回调（`K f9529f` 就是状态回调接口），因此 UI 能实时显示「运行中/暂停/失败原因」。

## 7. 前置条件检测（已见 + 推断）

- 是否被选为模拟位置应用：`MainActivity` 第 1294-1298 行 `Y()`，取 `AppOpsManager`，Android 10+ 用 `unsafeCheckOpNoThrow("android:mock_location", uid, pkg)`，更早的版本用 `checkOpNoThrow(...)`，返回 `MODE_ALLOWED` 才算通过。
- `WRITE_SECURE_SETTINGS` 声明在清单里（第 21 行）。本次没有在自有代码里找到写 Secure Settings 的调用点（`Settings.Secure.putString` 的命中都在第三方库），因此它大概率是历史遗留或为个别 ROM 预留；这一点标为未确认。
- 自检面板（`self_check_*` 一组文案）要求的项：开发者选项、模拟位置应用、位置权限、通知权限、系统定位开关、电池优化白名单。每项都带「已通过/建议/必需」三态与跳转按钮。

## 8. 数据持久化（已见）

- Room 数据库 `mock_location.db`（`sources/com/example/mocklocation/data/AppDatabase_Impl.java` 第 33 行）。
- 记录实体 `Record(id, name, latitude, longitude, type, timestamp)`（`data/Record.java`），`type` 是枚举 `I0.i`，只有两个值：`HISTORY`、`FAVORITE`（`sources/I0/i.java`）。
- DAO 能力（`data/RecordDao.java`）：按坐标查重、插入、更新（改名）、按类型分页查询、按 id 删除。
- 设置与临时状态走 SharedPreferences，已见键名：`pref_map_provider`、`pref_self_check_completed`、`pref_review_total_success`、`pref_review_button_dismissed`、`state_route_latitudes`、`state_route_longitudes`、`state_route_speed`、`state_route_loop`、`trial_enabled`、`trial_duration_hours`、`subs`。

## 9. 计费与实验开关（已见）

- Google Play Billing 8.0.0；订阅商品 id 为 `mock_location_monthly` 与 `mock_location_yearly`，本地兜底价格 US$4.99/月、US$12.99/年（`subscription_price_*`）。
- 开始模拟前会经过 `u0(LatLng)` 的「订阅门」：Billing 客户端就绪后检查订阅态，已订阅才真正下发 START_MOCK；另有 `trial_enabled`/`trial_duration_hours` 两个 Firebase Remote Config 驱动的试用开关。
- Firebase Remote Config 还负责价格与试用天数，Firebase Installations/Firestore 承担安装统计。

## 10. 这套机制对复刻意味着什么

需要原样复刻的是前 8 节：模拟位置应用授权、双 provider 注入、GMS Fused mock、1 秒 tick、路线插值推进、前台服务与通知、AppOps 自检、记录持久化。第 9 节（计费与 Firebase 实验）属于商业分发能力，不是模拟定位功能本身，复刻版会用「免费可用」替代，并在规格文档里显式标注为差异。

不依赖私有 key 就能完整复刻的部分：全部注入逻辑、状态机、路线算法、自检判定、持久化、通知。
依赖私有 key/SDK 才能原样复刻的部分：百度地图渲染与地理编码（需要 `com.baidu.lbsapi.API_KEY`）、Google 地图（需要 Google Maps key 与设备上的 Google Play 服务）、Firebase 与 Play Billing（需要 Google Cloud 项目与上架资质）。
